# 闲鱼商家运营 Agent —— 技术方案（v0.1 草案）

> 📦 历史调研快照（2026-10-20）。结论已并入 [STATUS.md](STATUS.md) 与 [architecture.md](architecture.md)，保留作证据；当前状态不必读本文。

> **状态：部分被 [ADR 0001](adr/0001-base-on-dsh.md) 取代。** 本文的三层架构、性能预算、通道策略、风险边界仍然有效；但包名与目录以 ADR 为准（`packages/{core,daemon,plugin-ops,ops-bundle}`，统一 `@bigfish/*`），交付形态是 bundle + Cordis 插件，不是"往 DSH 仓里塞一个 dsh-plugin"。
>
> 目标：给个人商家做一条"24 小时在线的运营助手"，形态是 **DSH 插件 + 本地运营内核（daemon）**。
> 主线：帮商家**上架、擦亮、改价、回消息、发货、出日报**，而不是做数据采集/倒卖。
> 本文回答三件事：能不能做、怎么架构、性能预算与风险边界。

## 0. 结论

| 问题 | 结论 |
|---|---|
| 技术上能不能做 | **能。** 抓取（详情/我的商品/订单）1–2 天可出 demo；发布有 3 条通道，见 §4。 |
| 做成 DSH 插件合不合适 | **合适**，DSH 的扩展点刚好覆盖：工具注册、后台任务、定时唤醒 agent、GUI 卡片、凭据保管。 |
| 24 小时在线 | **可行，但要拆层**：确定性操作放 daemon（轻、常驻），LLM 决策放插件（按需唤醒）。DSH 桌面端关闭时 daemon 仍可跑确定性动作，但无人格化决策。 |
| 用户性能 | 空闲额外占用目标 **< 150MB / < 1% CPU**；浏览器实例只在发布瞬间起，用完即退；LLM 有日预算。 |
| 最大风险 | 平台协议 → 封号；逆向签名/绕过风控的合规边界；GPL/AGPL 代码传染；闲管家开放平台有资质门槛。 |

**一句话**：这是一个"运营自动化"产品，技术不难，难在**通道稳定性 + 风控节奏 + 合规定位 + 长期维护成本**。

## 1. 为什么是 DSH 插件

已核实的 DSH 扩展点（源码 `C:/Users/34239/Documents/GitHub/deepseek-harness`）：

- **工具**：`ctx.tools.register(defineTool({ name, description, parameters, output, execute }))`，注册是 effect，dispose 自动注销；工具 schema 自动进系统提示。
- **后台长任务**：`ctx.jobs.start({ kind, label, owner: exec.agent, run })`，自带 `job_kill` / 进度 / 输出回读，不占前台。
- **定时唤醒 agent**（关键）：插件定时器触发 → agent 空闲时 `agent.followup(createUserMessage(...))`，忙碌时 `agent.inject({ content, source: { kind: 'plugin', plugin: 'xy-ops' } })`。官方 cookbook 明确把这套列为 "定时任务（cron）" 的标准做法。
- **凭据**：`ctx.credentials` seam，登录 cookie 不必明文落盘。
- **设置**：`ctx.settings` 管每个商家的偏好（自动发布开关、日预算、最低价线）。
- **GUI**：client-module 注册面板/卡片，可做"待审批发布单"列表与一键批准；审批可走 `ctx.approval` / `tools/pre-execute` 返回 `ask`。
- **能力缝**：`tools/pre-execute` 做发布/改价这类高危动作的分级拦截（dry-run / 需批准 / 全自动）。
- 最小插件形态：

```ts
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'dsh-xianyu-ops'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'xy_status',
    description: '店铺运营概览：在售/曝光/待发货/待回复/异常',
    parameters: {},
    output: { schema: { type: 'object' }, render: (_a, v) => [{ type: 'text', text: JSON.stringify(v) }] },
    async execute(_args, exec) { return daemon.get('/status', exec.signal) },
  }))
}
```

结论：**"agent 一样的工具" 不用自己造 agent 框架**，DSH 就是宿主，插件提供领域工具 + 定时唤醒 + 面板。

## 2. 总体架构（三层）

```
┌──────────────────────────────────────────────────────────────┐
│ ① Agent 决策层（DSH 插件内，LLM）                            │
│   写文案 / 议价 / 异常研判 / 日报 / 需要判断的排期            │
│   工具: xy_*  ; cron → followup() 唤醒 ; cron → inject()    │
└───────────────▲──────────────────────────────────────────────┘
                │ localhost HTTP/WS + token（仅本机）
┌───────────────┴──────────────────────────────────────────────┐
│ ② 运营内核 daemon（独立 Node 进程，无 LLM，常驻）             │
│   登录态保活 / IM WebSocket / 定时擦亮改价 / 订单发货          │
│   发布流水线（类目属性/违禁词/图片上传/提交）                  │
│   SQLite 事件库 + 任务队列 + 审批队列                          │
└───────────────▲──────────────────────────────────────────────┘
                │ 三条通道（可切换）
   ┌────────────┴────────────┬───────────────────┬────────────┐
   │ A 官方闲管家开放平台      │ B mtop 接口直连    │ C 浏览器自动化 │
   │ 稳定、要资质、QPS 10     │ 轻、快、需签名     │ 最稳风控、吃内存 │
   └─────────────────────────┴───────────────────┴────────────┘
```

**为什么要拆 daemon：**
1. **性能**：DSH 桌面端是 Electron，UI 关掉/卡住时运营不能停；daemon 独立、可被系统服务/开机自启托管。
2. **成本**：24 小时跑 LLM 会烧钱；90% 的运营动作是确定性的（擦亮、发货、模板回复），不该过模型。
3. **稳定**：浏览器崩溃、接口报错被隔离在 daemon，不会拖垮对话。
4. **可测试**：daemon 的 HTTP API 可以脱离 DSH 单独跑集成测试。

插件与 daemon 的关系：插件是 daemon 的**唯一客户端**（`127.0.0.1` 随机端口 + `~/.xianyu-ops/token` 鉴权），不暴露公网。

## 3. 24/7 怎么落地

| 机制 | 做法 |
|---|---|
| 进程常驻 | daemon 由插件首次启动时拉起并 supervise（心跳/重启）；可选安装为登录启动项（Windows 计划任务 / 用户级启动目录）。 |
| 定时任务 | daemon 内部 cron（`node:timers` + 持久化 nextRun），不与 DSH 生命周期绑定。 |
| Agent 唤醒 | 插件 cron tick：先查 daemon `/decisions/pending`；有需要判断的任务才 `followup()`，没有则**不发任何模型请求**（零 token）。 |
| 忙碌处理 | agent 正在跑时改用 `inject()` 排队，下一次模型请求看到；不抢占。 |
| 睡眠/断网 | 队列持久化在 SQLite；醒来按"到期一次、不补跑"策略执行，避免雪崩。 |
| 崩溃恢复 | daemon 重启后扫 `jobs` 表：进行中的发布标 `needs_review`（发布不可盲目重试，先查平台侧状态）。 |
| DSH 未开 | 确定性动作照常；`decisions` 累积，下次打开时批量呈现/处理。 |
| 登录过期 | 检测到 `FAIL_SYS_SESSION_EXPIRED` → 停止写操作 → 插件 inject 通知 + GUI 二维码卡片；恢复后自动续跑。 |

## 4. 发布通道怎么选（核心决策）

| 维度 | A 官方闲管家 | B mtop 直连 | C 浏览器（CDP 接管已登录 Chrome） |
|---|---|---|---|
| 稳定性 | 高（有文档、回调） | 中（接口/签名会变） | 中高（页面 DOM 会变） |
| 风控风险 | 低 | **中高**（非官方调用） | 低（真人浏览器指纹） |
| 性能 | 极轻（纯 HTTP） | 轻（30–60MB） | 重（+200–400MB，5–20s/次） |
| 开发量 | 中（要资质/签名/回调） | 高（sign、tfstk、protobuf IM） | 低中（Playwright 填表） |
| 门槛 | 鱼小铺 + 订购 ERP 专业/铂金版，有发布上限 | 无，但账号需登录态 | 无 |
| 适用 | 有资质的商家 | 读操作、批量、高频 | 发布主通道、兜底 |

**推荐混合策略**
- **读写分离**：读（商品、订单、IM、曝光）走 B，便宜快；写发布主走 C，把风控压力交给真实浏览器。
- **有资质就上 A**：官方通道是唯一"不会因协议被封"的路，值得作为商用版本的高价档。
- **B 只做低风险调用**：列表/详情/IM 拉取；发布接口保留但默认关闭，作为灰度实验开关。
- **C 的实现要点**：优先 CDP 接管用户**已登录**的 Chrome（零额外内存、零登录态搬运），否则用独立 user-data-dir 起 `playwright-core`；遇滑块/人脸 → 转人工，不硬刚。

## 5. 功能域（MVP → 完整）

| 模块 | 能力 | 自动化级别 |
|---|---|---|
| 上架发布 | 图片/Excel/网盘 → 识别 → AI 标题/描述/标签 → 违禁词与图片合规 → 类目属性映射 → 价格建议 → 排期发布 | 默认**待审批**；可开全自动 + 每日上限 |
| 运营巡检 | 曝光/想要/浏览下滑预警 → 建议改价/换首图/擦亮/重发 | 擦亮、定时下架 = 自动；改价 = 限额内自动 |
| 客服 IM | 商品问答、库存/发货时效、议价（带最低价保护）、敏感词转人工 | 模板/知识库命中自动，其余 LLM 草稿待确认 |
| 订单 | 虚拟商品自动发货（卡密）、发货提醒、超时预警、评价邀请 | 自动 + 异常转人工 |
| 日报 | 每日 9:00 经营简报：GMV、曝光、转化、待办 | 自动（cron → followup → 生成后 inject） |
| 合规巡检 | 违禁词库、类目错放、盗图风险、频繁改价自查 | 自动出报告 |

**审批边界（默认值，可配）**
- 必须人工：首次发布、价格低于成本线、退款/纠纷回复、多件批量操作 > 20 条。
- 可自动：擦亮（平台次数内）、模板回复、卡密发货、日报、下架已售罄。
- 全部动作写 `audit` 表（谁/何时/参数/结果），可回放、可撤销（改价可 revert）。

## 6. 性能预算（目标值，非实测）

| 项 | 空闲 | 忙时（发布一次） | 控制手段 |
|---|---|---|---|
| daemon RSS | 50–90MB | +20MB | 单进程；SQLite WAL；WS 单连接；不缓存图片 |
| daemon CPU | <1% | 2–5% 峰值 | 无轮询（事件驱动 + 定时器）；图片处理丢 worker_threads |
| DSH 插件 | 20–40MB | 同 | 只做工具与转发，不跑业务循环 |
| 浏览器 | 0（未启动） | +200–400MB / 20–60s | 单实例串行；用完即退；优先 CDP 接管已开 Chrome |
| LLM | 0（无任务不请求） | 按任务 | 规则优先；夜间静默（23:00–08:00 只做确定性）；日 token 预算硬上限；相同任务去重 |
| 磁盘 | <50MB | 图片临时目录 <500MB | 发布成功即删临时图；SQLite 定期 VACUUM |
| 网络 | 心跳 1 次/60s | QPS ≤1/账号，抖动 ±30% | 全局限速器；夜间降频；失败指数退避 |

额外原则：
- **单机单账号**优先；多账号会让设备指纹关联，风险指数上升，也翻倍资源。
- GUI 面板走 DSH 现有 Web Client，不额外起服务。
- daemon 日志滚动（10MB×3），避免长期跑爆盘。

## 7. 代码结构建议（monorepo）

```
big fish/
├─ packages/
│  ├─ core/            # 通道抽象 + 领域模型 + 风控节奏（限速/退避/抖动）
│  │  ├─ channels/     # official.ts / mtop.ts / browser.ts
│  │  ├─ publishers/   # 上架流水线（校验→上传→提交→回读）
│  │  └─ db/           # SQLite schema + migrations
│  ├─ daemon/          # 常驻进程：HTTP API + cron + IM WS + 队列
│  ├─ dsh-plugin/      # DSH 插件：xy_* 工具 + cron→followup + client 卡片
│  └─ shared/          # 类型、协议、校验（zod）
├─ docs/               # 本文、接口文档、合规说明

```

技术选型：Node 24、TypeScript、`better-sqlite3`（同步 API 够用且快）、`ws`、原生 `fetch`、`sharp`（worker 里跑）、`playwright-core`（CDP attach）、`zod`。**不引入重型框架**，保持 daemon 启动 <300ms。

## 9. 风险与合规（必须提前定调）

1. **平台协议与封号**：自动化发布/批量操作违反闲鱼用户协议，最坏结果是限流/封号。缓解：单账号、低频、拟人节奏、默认人工确认、给用户明确风险告知与"熔断开关"。
2. **法律边界**：操作**自己的**账号，民事违约风险为主；但"逆向签名、绕过 tfstk/风控"在对外售卖工具时可能落入"提供侵入/非法控制计算机信息系统程序、工具"的争议区（刑法 285 条边缘）。**对外商业化时，优先官方通道，把逆向通道定位为自用/实验。**
3. **开源许可**：`shaxiu/XianyuAutoAgent`（GPL-3.0）、`zhinianboke/xianyu-auto-reply`（AGPL-3.0）、`23Star/xianyu-super-butler`（AGPL-3.0）**不能抄代码**，只能参考思路；可用 MIT 的 `cv-cat/XianYuApis`（签名/mtop 参考，仍建议自研关键实现）。
4. **个人信息**：买家昵称/头像/聊天记录属个人信息，本地存储需最小化 + 加密 + 可删除；不做跨商家数据聚合。
5. **稳定性依赖**：接口/DOM 随时变，需要"选择器与接口指纹"版本化 + 每日自检探针（发现失效 → 自动降级到备用通道 → 通知）。
6. **闲管家门槛**：没有鱼小铺资质的个人卖家走不了 A，产品要能无 A 运行。

## 10. 待确认（影响架构的三个决策）

1. **目标商家**：纯个人卖家（无鱼小铺）为主，还是也覆盖有资质商家？→ 决定是否第一批就做官方通道。
2. **首发主打**：先做"批量上架"还是"客服+擦亮"？→ 前者重发布通道，后者重 IM 稳定性。
3. **运行形态**：接受"DSH 桌面端 + daemon 开机自启"（推荐，开发快），还是要求纯后台服务 + 独立 Web 管理台（更重，但商家不装 DSH 也能用）？
